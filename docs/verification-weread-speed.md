# 读书想法获取性能验证

日期：2026-09-17

版本：1.6.6

## 原因与修复

1.6.5 逐章获取完整范围后，每章需先获取划线，再分批请求段评和后续分页，最后获取章评。
所有章节串行；每批只有 5 个范围，且批次末尾、章节末尾、后续分页还各自等待。
这能解释慢速来源，但没有在用户网络下实测各接口延迟。

本次采用最多三个章节 worker 和一个共享 HTTP 调度器。各章内部依赖关系、段评后续分页和原始阅读顺序不变。
大批次最多包含 30 个范围，遇到参数错误回退五个范围，其他网络/鉴权错误不盲目拆分重试。

共享调度器约束：

- 请求启动间隔至少 200ms，最多三个在途请求。
- 覆盖章节范围、段评、分页、章评、书评、网关回退及内部重试。
- 接收到 429 或 -2014 后，所有任务共享冷却截止时间；支持 Retry-After 秒数和 HTTP 日期。
- 冷却后降为一个在途请求，启动间隔增至 600ms。
- 单请求最多三个限流尝试；服务端要求等待超过十秒或持续限流时停止本轮新请求，保留现有数据并提示未完成，不绕过冷却。
- 等待队列与实际网络超时分开计算；底层网络超时为三十秒并发出取消信号。
- 关闭客户端后不再启动排队请求或领取剩余章节。
- 登录及普通搜索不主动启用同步调度；同一客户端不允许重叠启动两个同步任务。

## 自动测试

`test/weread_sync_client_test.dart` 验证：

- 十二个请求的启动间隔与在途上限。
- 429 全局等待、POST 请求体重放和降并发。
- HTTP 200 中的 -2014 业务限流。
- Retry-After 要求长等待时停止后续请求。
- 重复限流有限重试、重叠同步拒绝。
- 关闭客户端后不再发送队列中的请求。

`test/weread_sync_performance_test.dart` 验证：

- 九章并行处理最多三章，保留 108 条不同段评、全部章评和原始章节顺序。
- 大批次拒绝后退回五个范围，已获取的评论不丢失。
- 用真实 WereadApi + MockClient + 固定 300ms 请求延迟测试完整 HTTP 流程；
  六章各十二个段落共 72 条段评，无跨章串数据、无不完整警告。

一次本机受控 HTTP 结果：

```text
chapters=6 paragraphs=72 networkDelayMs=300
requests=14 peak=2 elapsedMs=3131
```

14 次请求包括章节列表、热门划线补充以及六章各自的范围和段评请求；本场景关闭章评/书评，以隔离段评主流程。
不通过绝对耗时阈值判断测试成功，断言以数据完整性、批次数和并发边界为准。
该结果不是微信读书实网基准，也不能外推为三千章整书完成时间。

最终串行全量回归 291 项通过、21 项因夹具或显式输入要求跳过、0 失败，约 108 秒。
应用源码和新增测试静态分析无问题。

## 多 IP 范围

本次没有接入代理池，没有购买或调用公共代理，也没有向新服务发送账号凭据。
用户尚未提供可信出口。是否添加多出口应另行确认代理来源、认证和平台允许的用法；
不能假定平台只按 IP 限流，更不能承诺换 IP 后能消除账号侧限制。
